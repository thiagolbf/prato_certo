## Findings detalhados

### 🔴 Bloqueantes

### 🟡 Importantes

#### R-01 — A API não atende dois estabelecimentos; o isolamento só existe nas consultas

- **Eixo:** 3. Aderência ao spec (ADR-003, RN-41)
- **Evidência:** `api/app/core/estabelecimento.py`, `estabelecimento_atual`, levanta `RuntimeError` quando há mais de um estabelecimento. Todas as rotas resolvem o estabelecimento por esta função. O docstring diz "a partir da T-10, passa a vir do usuário autenticado", mas a T-10 não implementou essa troca.
- **Descrição:** o isolamento entre estabelecimentos é garantido pelos repositórios e consultas, que filtram pelo `estabelecimento_id` recebido. Mas a camada HTTP não consegue atender um segundo estabelecimento: com dois cadastrados, toda rota falha. O CA-33, escrito para a API, só está coberto na camada de consulta.
- **Por que é Importante:** o docstring promete uma troca que não aconteceu, e o teste de CA-33 não exercita a API.
- **Sugestão de correção:** decidir com o dono do produto se a implantação é sempre de um estabelecimento (então o docstring e o CA-33 devem refletir isso) ou se o multi-estabelecimento é requisito. Se for requisito, criar uma tarefa própria que resolva o estabelecimento a partir da sessão do usuário, em todas as rotas, com teste HTTP de isolamento.

#### Ressalva de escopo

A decisão acima não foi tomada nesta rodada, porque muda a forma de resolver o estabelecimento em todas as rotas. Ela fica registrada como pendência para o dono do produto.

### 🟢 Sugestões

#### R-02 — Renovação de sessão é a única escrita em um GET

- **Eixo:** 5. Qualidade
- **Descrição:** `GET /api/auth/me` e as demais rotas autenticadas renovam a expiração da sessão em uso (RN-36), o que grava na tabela `sessao`. O inventário exclui essa tabela de propósito. Trata-se de decisão de desenho que deve ser confirmada, porque ADR-006 diz que alteração de estado nunca é feita por GET.
- **Sugestão de correção:** confirmar com o dono do produto que a renovação em uso é aceita como exceção, e registrar a exceção na arquitetura.

#### R-03 — O inventário usa valores fixos para parâmetros de caminho

- **Eixo:** 4. Cobertura de teste
- **Descrição:** cada parâmetro de caminho é trocado por `1`. Rotas que pedem ids inexistentes respondem 404 sem gravar nada, então o teste não cobre as rotas com ids reais. Os dados semeados cobrem os fluxos principais.
- **Sugestão de correção:** semear ids reais para os caminhos quando o catálogo crescer.

- **RN-42:** coberta pelo inventário (ver R-02 sobre a renovação de sessão).
